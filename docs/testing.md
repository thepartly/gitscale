# Testing

gitscale has two kinds of tests:

- **Unit tests** sit beside the code they test, in `#[cfg(test)]` modules under
  `src/`.
- **Integration tests** run real commands against real git repositories and a
  fake OCI registry. They live in one test binary, `tests/it/`, with one module
  per feature.

Every test is listed in the [test catalog](test-catalog.md), which is generated
from the sources.

## Running

```text
cargo test                               # everything
cargo test --test it                     # integration tests only
cargo test --test it pull::              # one feature
cargo test --test it pull::edge_         # one kind of case in one feature
cargo test --test it ::error_            # one kind of case in every feature
cargo test --test it pull::edge_007      # one test, with its variants
cargo test --test it -- --ignored        # the ignored tests: known failures and slow ones
```

The conformance tests in `registry` talk to a real registry, and skip
themselves unless `GITSCALE_TEST_REGISTRY` names one:

```text
docker compose up -d registry
GITSCALE_TEST_REGISTRY=localhost:5000 cargo test --test it registry::
```

Where `localhost:5000` is refused — inside the devbox or an agent sandbox —
use the service name instead: `GITSCALE_TEST_REGISTRY=registry:5000`.

## Naming

An integration test is named

```text
<feature>::<kind>_<id>[<variant>]_<sentence>
```

for example `pull::edge_007_refuses_to_lose_commits_made_at_a_pin`.

- **feature** is the module the test lives in: the behaviour that would break
  if the test failed, not the command the test happens to run. A pull that
  must update the CI cache is a `cache` test.
- **kind** is one of:
  - `normal` — what the feature is for, on ordinary input.
  - `edge` — unusual state or input the feature must still handle: odd paths,
    work in the way, interrupted runs, boundaries.
  - `error` — a refusal or a failure: what must be reported, and what must be
    left untouched.
  - `perf` — how much work it does: downloads, fetches, requests, processes.
    Assert on counts, which are exact, rather than on time.
- **id** is three digits, unique within the feature. It is never reused: a
  removed test leaves a gap, and a new test takes the next number after the
  highest. Moving a test to another kind keeps its id. Its catalog id is
  `<feature>-<id>`, for example `pull-007`.
- **variant** is a letter, `a`, `b`, …, for tests that look at one scenario
  from different angles, such as a refusal without `--force` and the same
  case with it. Tests that differ only in their input are better written as
  one test over a list of inputs.
- **sentence** says what holds, in plain words.

Give each test a doc comment when the name alone does not say why the
behaviour matters. The catalog shows its first paragraph.

## Ignored tests

A test that is ignored says why, and the reason starts with one of:

- `bug:` — a known failure. The test states the right behaviour and fails
  until the bug is fixed; remove the `#[ignore]` with the fix.
- `slow:` — too slow for every run.

```rust
#[test]
#[ignore = "bug: develop --stop deletes unpushed commits on the topic branch"]
fn error_014_stop_keeps_unpushed_commits_on_the_branch() { ... }
```

## The catalog

`docs/test-catalog.md` is generated by `tests/it/catalog.rs`, which also
checks the naming rules. After adding, renaming or removing a test:

```text
GITSCALE_UPDATE_CATALOG=1 cargo test --test it catalog::
```

Commit the catalog with the change, so a removed test shows in the review.

## Writing a test

- Start from `support::TestEnv`. It gives each test its own playground, bare
  remotes, cache directory and fake registry, named after the test and the
  process, so tests run in parallel.
- Pass a name to `TestEnv::new` that no other test uses.
- Helpers shared by several features go in `tests/it/support/`.
- In-process runs (`TestEnv::run`) share the process environment. A test that
  needs environment variables — `CI`, `HOME`, a job token — runs the binary as
  a subprocess (`TestEnv::run_with_env`).
- Never touch the developer's own home directory, git config or registry
  credentials. `.cargo/config.toml` already isolates the system git config,
  the cache, Docker credentials and CI variables.
